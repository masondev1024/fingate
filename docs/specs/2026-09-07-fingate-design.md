# FinGate 설계 — 계약 위반 데이터를 차단하는 금융 서빙 파이프라인

- 작성일: 2026-09-07
- 목표 제출: 2026-09-18 (서류), 이후 실무 면접
- 저장소: `fingate` (신규)

---

## 1. 한 줄 정의

한국은행 ECOS의 거시 금리와 금감원 DART의 보험사 재무를 수집·정규화해 서빙하되, **계약을 위반한 데이터가 서빙에 도달하는 것을 증명 가능하게 차단**하고, 차단된 건은 담당자 승인을 거쳐야만 통과시키는 파이프라인.

## 2. 왜 이 문제인가 — 실측된 근거

데이터 엔지니어 포트폴리오는 대부분 "수집해서 적재했다"로 끝난다. 금융에서 진짜 어려운 것은 적재가 아니라 **거부**다. 잘못된 수치로 산출한 지표는 규제 사고가 된다.

그리고 이 위험은 추상적이지 않다. 2026-09-07에 두 API를 직접 호출해 확인한 사실:

| 요청 | HTTP | 실제 본문 |
|---|---|---|
| ECOS, 잘못된 인증키 | **200** | `{"RESULT":{"CODE":"INFO-100","MESSAGE":"인증키가 유효하지 않습니다..."}}` |
| ECOS, 존재하지 않는 통계표 코드 | **200** | 오류 페이로드 |
| DART, 잘못된 인증키 | **200** | `{"status":"010","message":"등록되지 않은 인증키입니다."}` |
| DART `corpCode.xml`, 잘못된 인증키 | **200** | 150 bytes XML 오류 (정상은 3,601,634 bytes zip) |

**두 API 모두 모든 오류에 HTTP 200을 반환한다.** `raise_for_status()` 만 믿는 수집기는 오류 페이로드를 데이터로 적재한다. `corpCode.xml` 은 특히 위험하다 — 3.6MB zip을 기대하는 자리에 150바이트가 와도 상태 코드는 같다.

이것이 이 프로젝트의 출발점이다. 가정이 아니라 실측이다.

## 3. 범위

### 대상 데이터

| 소스 | 대상 | 주기 |
|---|---|---|
| ECOS `722Y001` | 한국은행 기준금리 및 여수신금리 | 일 |
| ECOS `817Y002` | 시장금리 | 일 |
| ECOS `121Y006` | 예금은행 대출금리(신규취급액) | 월 |
| DART 재무제표 | 보험 5사 × 최근 5개 사업연도 | 연 |

보험 5사: 한화생명 `00113058`, 한화손해보험 `00135917`, 삼성생명 `00126256`, DB손해보험 `00159102`, 현대해상 `00164973`

보험사를 고른 이유는 수익 구조가 금리에 직결되어 두 소스의 조인이 도메인적으로 의미를 갖기 때문이다.

### 포함

- 3계층 계약 게이트(응답·스키마·품질)와 fail-closed 차단
- 차단 건에 대한 담당자 승인/반려 경로와 감사 로그
- last-known-good 스냅샷과 `degraded` 상태 명시 서빙
- 요청 → 행 계보(lineage) 추적
- Fault injection 실험과 차단율 측정

### 명시적 비목표 (YAGNI)

- LLM·에이전트 (이 프로젝트는 파이프라인이다)
- 실시간 스트리밍
- 투자 판단·신용평가 모델
- 웹 UI (승인은 CLI로 한다)
- 클라우드 배포 (로컬 재현이 목표)

## 4. 아키텍처

```
  ECOS API ─┐
            ├─→ Collector ─→ Raw store (원본 + request_id + sha256 + 수신시각)
  DART API ─┘       │
                    │  [계약 1] 응답 계약: HTTP 200 != 성공
                    ↓
              Normalizer ─→ bronze (정형화, XBRL/zip 파싱 포함)
                    │
                    │  [계약 2] 스키마 계약: 필드·타입·단위
                    ↓
              Quality gates ─→ silver
                    │
                    │  [계약 3] 품질 계약: 값 범위·신선도·중복·결측
                    ↓
              위반?  ──예──→ StagedException ──→ 담당자 승인/반려
                    │                                   │
                   아니오                          감사 로그(사유 필수)
                    │                                   │
                    ↓                        승인 시에만 통과 ┘
              Serving snapshot (last-known-good, degraded 명시)
```

저장은 **DuckDB**(bronze/silver/serving)와 파일시스템(raw 원본 보존)을 쓴다. 원본을 지우지 않는 이유는 계보 추적과 재현 가능한 백필 때문이다.

## 5. 3계층 계약

계층을 섞지 않는 것이 핵심이다. 각 계층은 서로 다른 실패를 잡는다.

### 5.1 응답 계약

HTTP 200은 성공을 의미하지 않는다.

- ECOS: 본문에 `RESULT.CODE` 가 있으면 실패로 판정
- DART: `status != "000"` 이면 실패로 판정
- `corpCode.xml`: 응답이 zip 시그니처로 시작하고 최소 크기를 넘는지 확인
- 위반 시 적재 중단. 원본은 보존하고 실패 사유를 기록한다

### 5.2 스키마 계약

지표별로 필드 존재·타입·단위를 선언하고 위반 시 적재를 거부한다. DART 재무제표는 계정과목명이 회사·연도마다 흔들리므로 **표준 지표로의 매핑을 명시적으로 선언**하고, 매핑되지 않은 계정은 조용히 버리지 않고 미매핑으로 기록한다.

### 5.3 품질 계약

| 검사 | 예 |
|---|---|
| 값 범위 | 기준금리가 −100% 이거나 999% 일 수 없다 |
| 신선도 SLA | 일별 지표가 N일 이상 갱신되지 않으면 위반 |
| 중복 키 | 같은 (지표, 일자)가 두 번 |
| 결측률 | 기간 내 결측 비율 상한 |
| 급변 | 전일 대비 변화폭이 사전 등록 임계 초과 |

## 6. 승인 게이트

품질 계약 위반은 자동으로 서빙을 막는다. 그러나 실제 운영에서는 **정당한 급변**이 있다(정책금리 인상, 회계기준 변경). 그래서 차단으로 끝내지 않고 사람이 판단할 경로를 둔다.

`StagedException` 은 다음을 갖는다.

- 위반한 계약과 실제 값·임계값
- 관련 원본 `request_id`
- 담당자 결정: 승인(override) 또는 반려. **사유 필수**
- 만료 시각. 오래된 승인은 재사용할 수 없다

승인 없이는 통과하지 않고, 모든 결정은 감사 로그에 남는다. 자동 통과 경로가 있어도 기록은 예외 없이 남는다.

이 구조는 Weathervane 프로젝트의 `StagedChange` 와 같은 형태다. 자동 판단은 제안이고 실행은 사람이 승인한다는 원칙을 파이프라인에 이식한 것이다.

## 7. 서빙

- 계약을 통과한 스냅샷만 서빙한다
- 신선도 위반 시 낡은 값을 조용히 내보내지 않는다. **last-known-good을 유지하되 `degraded` 상태와 마지막 정상 시각을 함께 노출**한다
- 서빙 응답에 계보(`request_id`)를 포함해 어떤 원본 요청에서 나온 값인지 추적 가능하게 한다

## 8. 측정 — Fault injection 실험

이 프로젝트의 결과물은 "만들었다"가 아니라 **"얼마나 막았다"** 여야 한다.

오염 카탈로그를 **게이트를 구현하기 전에** 코드에 고정한다. 결과를 보고 카탈로그를 조정하면 측정이 무의미해진다.

| 오염 | 근거 |
|---|---|
| 인증 실패 응답 | 실제 API가 HTTP 200으로 반환 (실측) |
| 존재하지 않는 통계표 코드 | 실측 |
| zip 대신 오류 XML | 실측 (3.6MB → 150B) |
| 값 이상치 | 주입 |
| 신선도 위반 | 주입 |
| 중복 키 | 주입 |
| 스키마 변경(필드 삭제·타입 변경) | 주입 |
| 부분 결측 | 주입 |

**측정 지표: 게이트 없음 대비 게이트 적용 시, 오염 데이터의 서빙 도달률.**

목표치를 사전에 선언하지 않는다. 목표를 정하면 그 숫자를 맞추도록 게이트를 조정하게 된다.

## 11. 성공 기준

- 두 API에서 실데이터 수집 성공, 원본과 계보 보존
- 8종 오염 전부에 대해 어느 계층이 잡았는지 분류된 실험 결과
- 게이트 적용 전후 서빙 도달률 수치
- 신선도 위반 시 `degraded` 상태가 실제로 노출됨을 재현
- 승인 없이는 위반 데이터가 서빙되지 않음을 테스트로 증명
