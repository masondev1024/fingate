# 엔지니어링 기록 — 무엇이 깨졌고 왜 그렇게 정했나

설계 문서는 결과를 적는다. 이 문서는 **거기 도달하기까지 틀렸던 것**을 적는다.

각 항목은 증상에서 시작한다. 원인을 먼저 적으면 그것이 자명해 보이지만, 실제로는
증상만 보이는 상태에서 원인을 찾아야 했다.

수치는 전부 실측이다. 추정치나 기억으로 쓴 숫자는 없다.

---

## 1. 트러블슈팅

### 1.1 외부 API

#### T-01 · 오류를 HTTP 200으로 돌려준다

**증상** — 잘못된 인증키로 호출했는데 요청이 성공했다.

**원인** — ECOS와 DART 모두 오류를 HTTP 200으로 반환한다. 본문에 `INFO-100`(인증 실패),
`INFO-200`(없는 통계표) 같은 코드가 들어 있을 뿐이다. DART는 3.6MB zip이 와야 할 자리에
150바이트 오류 XML을 200으로 준다.

**처리** — 상태 코드가 아니라 **본문의 성공 코드**를 계약으로 삼는 응답 계층을 별도로 뒀다.
zip은 매직 바이트로 확인한다.

**교훈** — 상태 코드만 보고 파싱하면 오류 메시지가 데이터로 적재된다. 대조군 실험에서
이 방식은 오염 11종 중 10종을 그대로 서빙했고 1종에서는 크래시했다.

> 이 하나를 먼저 재보지 않았으면 프로젝트 전체가 잘못된 전제 위에 세워졌을 것이다.

#### T-02 · 응답이 빠를수록 위험하다

**증상** — DART를 25번 연속 호출한 뒤 모든 요청이 `status=101`(접근 제한)로 막혔다.

**원인** — DART 응답 p50이 **0.12초**다. 페이싱 없이 순차 호출하면 초당 8건이 나간다.
빠른 응답이 곧 여유가 아니라, 오히려 스스로를 차단시키는 속도를 만든다.

**처리** — 응답 지연을 **먼저 측정하고** 그 위에 페이싱을 설계했다(`collect/pacing.py`).
재시도는 일시적 오류에만 적용한다(`TRANSIENT_STATUS_CODES = {"101", "020", "800"}`).

**교훈** — 호출 간격을 지연에서 유도하지 말고 **제공자의 한도**에서 유도해야 한다.
지연이 짧을수록 페이싱이 더 필요하다.

#### T-03 · 단위 라벨이 계열마다 다르다

**증상** — 같은 연이율인데 계열마다 단위 문자열이 달랐다.

**원인** — 대부분 `연%`인데 가계대출금리만 `연리%`다.

**처리** — `unit`(정규화된 의미)과 `source_unit`(API가 실제로 보내는 라벨)을 분리하고,
계열마다 관측된 라벨을 선언해 **라벨이 바뀌면 계약 위반으로 잡는다**.

**교훈** — 표기가 일관되리라 가정하지 않는다. 다만 불일치를 무시하지도 않는다.
정규화하되 원본 라벨을 계약으로 감시한다.

### 1.2 데이터의 의미

#### T-04 · 응답 순서가 데이터의 의미를 정하고 있었다 ★가장 큰 결함

**증상** — 실제 보존된 DART 원본에서 자본총계를 절반으로 깎아 넣었는데 **품질 계약을
통과했다.** 막아야 하는데 통과했으니 구현이 틀린 것이다.

**원인** — DART는 같은 계정을 **연결재무제표(CFS)와 별도재무제표(OFS) 두 벌로** 보낸다.

```
자산총계: 2행
   fs_div=CFS (연결재무제표)  160,146,430,758,072
   fs_div=OFS (재무제표)      122,135,032,514,289
```

두 곳에서 중복이 조용히 접혔다.

- `check_financial_quality` 가 `{indicator_id: amount}` 로 접는다 → 마지막 행이 이긴다
- `load_financials` 의 PK 가 `(corp_code, bsns_year, report_code, indicator_id)` 다.
  `fs_div` 가 없다 → `ON CONFLICT DO UPDATE` 가 마지막 행으로 덮어쓴다

전 보존 응답을 셌다.

| | |
|---|---|
| CFS·OFS를 함께 반환한 보고서 | **56 / 56 (전부)** |
| 마지막-승자 규칙이 고른 기준 | **238 / 238 전부 OFS(별도)** |

창고 전체와 서빙 50행이 별도재무제표였다. 아무도 그렇게 정하지 않았고, 어디에도
기록되지 않았고, 문서에도 없었다.

**처리** — 연결(CFS)을 계약 기준으로 **선언**하고, `fs_div` 를 행에 기록하고, 선언한
기준이 없으면 다른 기준으로 대체하지 않고 차단한다. 다른 기준 행은 `OTHER_BASIS` 로 보존한다.

| 2024 총자산 | 이전(별도) | 이후(연결) | 차이 |
|---|---|---|---|
| 한화생명 | 122.1조 | **160.1조** | +38.0조 |
| 삼성생명 | 275.3조 | **312.2조** | +36.9조 |
| DB손해보험 | 52.9조 | **66.5조** | +13.6조 |

**교훈 — 이 프로젝트에서 가장 중요한 것**

회계 항등식(자산 = 부채 + 자본)이 50개 회사-분기 **전부에서 오차 0으로 성립**했다.
검증이 통과했으니 데이터가 맞다고 믿을 근거처럼 보인다. 그런데 **두 기준이 각자 균형을
이루므로 어느 쪽이 이겼든 그 안에서는 맞았다.**

> **검증이 통과했다는 사실은 검증이 옳다는 뜻이 아니다.**
> 통과하는 검증은 자신이 무엇을 보고 있는지 말해 주지 않는다.

이걸 찾은 건 코드 리뷰가 아니라 **오염 주입**이었다. 막아야 할 것을 실제로 막는지
재보지 않았다면 영원히 몰랐을 것이다.

#### T-05 · 보험사 재무가 2023년부터만 있다

**증상** — 조인 축을 연도로 잡았더니 2019~2022 구간이 통째로 비었다.

**조사** — API 제약인지 확인하려고 **삼성전자로 대조**했더니 2019~2022가 다 있었다.
보험사만 없다.

**원인** — **IFRS17 시행(2023)**에 따른 회계기준 단절이다. 이전 기준 데이터와 이후
데이터는 같은 축에 놓을 수 없다.

**처리** — 조인 축을 연도에서 **분기**로 바꿨다.

**교훈** — 데이터가 없을 때 "API가 안 준다"로 끝내면 안 된다. **다른 대상으로 대조**하면
제약인지 현상인지 갈린다. 이 한 번의 대조가 조인 설계를 바꿨다.

#### T-06 · 날짜 범위를 믿으면 틀린다

**증상** — 분기 손익 규모가 회사·보고서마다 들쭉날쭉했다.

**원인** — 보고서 종류마다 손익의 기간 의미가 다르다.

| 보고서 | `thstrm_amount` 의 의미 |
|---|---|
| 사업보고서 | **연간 전체** |
| 분기·반기보고서 | 해당 **3개월** |
| `thstrm_add_amount` | **누적** |

게다가 3분기보고서는 기간을 `2024.01.01~09.30`으로 표기하면서 금액은 3개월치를 준다.

**처리** — `period_kind`(POINT/QUARTER/ANNUAL)를 명시적으로 분리하고, 4분기 손익은
연간에서 3분기 누적을 빼서 유도하되 **유도값임을 플래그로 표시**한다.

검증: 한화생명 2024 Q4 = 866,000,982,115 − 727,008,758,067 = **138,992,224,048**

**교훈** — 필드 이름과 기간 표기는 의미를 보장하지 않는다. 규모가 이상하면 단위가 아니라
**기간 정의**를 의심한다.

### 1.3 통계와 판정

#### T-07 · "아무 peer나 동행하면 정상"은 틀린 규칙이다

**증상** — 금리 급변이 진짜인지 판정하려고 "연동 계열이 같이 움직였는가"를 보려 했다.
상식적으로는 "금리는 다 같이 움직인다".

**측정** — 기준금리가 실제로 바뀐 7일에 다른 계열이 동행했는지 셌다.

| peer | 동행 |
|---|---|
| 콜금리 | **7 / 7** |
| 국고채 3년 | 3 / 7 |
| 국고채 10년 | 3 / 7 |

**원인** — 국고채는 정책 결정을 **선반영**한다. 결정 당일에는 오히려 반대로 움직일 수 있다.
전체 쌍의 동행률에서도 기준금리↔국고채는 **0.429**로 동전 던지기보다 나빴다.

**처리** — peer 자격을 쌍별로, 그리고 **방향별로** 측정해서 정한다. 기준금리→콜금리는
성립하지만 역방향은 아니다(콜금리가 움직인 수백 일 대부분 기준금리는 그대로였다).

**교훈** — 상식은 가설이지 근거가 아니다. 재보면 절반이 틀린다.

#### T-08 · `corr()` 이 `nan` 인데 0으로 읽으면 정반대 결론이 난다

**증상** — 기준금리 × 월별 대출금리의 상관이 `nan`, 동행률이 `0.000`으로 나왔다.

**원인** — 월 시작일에는 기준금리 변동이 거의 없어 **분산이 0**이다. 상관이 정의되지 않는다.

**함정** — 동행률 `0.000`은 "완벽히 반대로 움직인다(= 매우 의심스럽다)"처럼 읽힌다.
실제로는 **"판단할 근거가 없다"**이다. 이걸 결함의 증거로 쓰면 정상 데이터를 결함으로 몬다.

**처리** — `nan` 과 빈 표본을 `INSUFFICIENT` 로 명확히 분리한다. 절대 `SUPPORTS_DEFECT` 로
흘리지 않는다. 테스트로 고정했다.

**교훈** — **근거가 없는 것과 반대 근거가 있는 것은 전혀 다르다.** 통계 함수의 특수값을
평범한 값으로 접으면 그 구분이 사라진다.

#### T-09 · 동행률만 보면 추세에 속는다

**증상** — 서로 무관하게 만든 두 합성 계열이 peer 자격을 통과했다. 테스트가 잡았다.

**원인** — 둘 다 대부분의 날 상승하는 계열이면 연동되지 않아도 부호가 자주 일치한다.

**처리** — peer 의 방향 편향만으로 우연히 맞출 확률을 **기대 동행률**로 계산하고,
실제 동행률이 그보다 얼마나 높은지(`lift`)를 게이트로 삼았다.

실측에서 갈림이 깨끗했다.

| | lift |
|---|---|
| 자격 쌍 최소 | **+0.186** |
| 탈락 쌍 최고 | **+0.106** |

**교훈** — 지표가 우연히 맞을 기저율을 빼지 않으면 그 지표는 신호를 재는 게 아니다.
이건 코드 리뷰가 아니라 **실패한 테스트**가 찾아냈다.

#### T-10 · 상관계수를 냈지만 신호가 아니라 잡음이다

**증상** — 금리 민감도 분석에서 회사별 상관계수가 −0.178 ~ +0.197로 부호가 갈렸다.

**원인** — IFRS17 단절로 비교 가능한 분기가 **9개**뿐이다.

**처리** — 결과를 지우지 않았다. 대신 **표본 수를 함께 출력하고 CLI가 경고를 찍는다.**

```
주의: 표본이 30분기 미만인 계열이 5개다. IFRS17 시행(2023)으로 보험사 재무가
2023년부터만 존재해 시점이 부족하다. 위 상관계수는 신호가 아니라 잡음으로 읽어야 한다.
```

**교훈** — 표본 수 컬럼을 뺐다면 그럴듯한 발견처럼 보였을 것이다. **약한 결과를 약하다고
표시하는 것이 결과를 지우는 것보다 정직하고, 숨기는 것보다 훨씬 정직하다.**

### 1.4 임계값

측정 없이 정한 임계는 **정상 데이터를 막는다.** 세 번 겪었다.

| 처음 정한 것 | 무슨 일이 났나 | 실측 | 바꾼 값 |
|---|---|---|---|
| 월별 신선도 SLA 60일 | 정상 데이터가 STALE로 차단 | 예금은행 금리는 익월 말 공표, 기간 시작일 기준 68일이 정상 | **95일** |
| 급변 임계 0.5%p | 기준금리 빅스텝 0.50%p는 실제로 있었던 정상 변동 | 11년치 분포 | **0.75** |
| 재무 급변 임계 (가정 시) | — | 총자산 분기 변동 −2.88% ~ **+8.73%**, p95 6.14% | **25%** (관측 최대의 약 3배) |
| 스프레드 경보 3σ (교과서 기본값) | 정상 데이터 900일 중 **11일(1.22%)** 오탐. 5σ도 3일(0.33%) | 콜금리×기준금리 스프레드는 꼬리가 두꺼워 **최대 6.51σ**. 국고채 쌍은 2.24σ | **쌍마다 관측 꼬리에서 유도** (관측 최대 ×1.2, 하한 4σ) |

**교훈** — 임계는 분포에서 유도한다. 그리고 **양쪽을 다 재야 한다**: 정상 데이터를
막지 않는가(거짓 양성), 막아야 할 것을 막는가(거짓 음성).

#### T-19 · 의심 관측이 자기가 비교당할 기준선을 오염시켰다

**증상** — 앵커 스프레드 probe 를 만들고 테스트를 돌렸더니, 0.9 급변을 주입한
시나리오에서 앵커가 **하나도 자격을 얻지 못했다**. 근거가 나와야 하는데 빈 목록이었다.

**원인** — 스프레드 표준편차와 관측 최대 이탈을 **전 구간**에서 계산했다. 의심 관측이
그 구간에 들어 있으므로, 이탈이 클수록 표준편차와 관측 최대치를 함께 키운다.
**클수록 자신의 허용치를 넓혀 스스로를 숨긴다.**

**처리** — 기준선 통계에서 판정 대상 시점을 제외한다(`exclude_period`).
동행률 쪽에도 같은 오염이 있어 함께 고쳤다 — 다만 변화량은 전 구간에서 계산하고
(`lag` 이 어긋나면 안 된다) 집계에서만 제외한다.

**교훈** — 이상치를 판정하는 통계에 그 이상치를 넣으면 안 된다. 당연해 보이지만
"전 구간 표준편차"는 자연스럽게 그렇게 쓰게 된다. **테스트가 아니었으면 못 찾았다.**

#### T-20 · 측정 방법이 틀려서 없는 오탐이 보였다

**증상** — 근거 고정 검증기의 오탐률을 쟀더니 39개 중 3개(7.7%)가 걸렸다. 전부
같은 형태였다 — `앵커는 있으나 2026-09-05 관측이 없어 …` 의 **날짜**.

**원인** — 내가 검증기에 probe 의 `facts` 만 넘겼다. 그런데 실제 도구는
`{probe, verdict, summary, facts}` 를 통째로 반환하고, **그 `summary` 문자열 안에
날짜가 들어 있다.** 시스템이 실제로 하는 대로 재지 않았다.

**처리** — 도구가 실제로 반환하는 형태로 다시 측정했다. 오탐 **0**.
그리고 이 성질(요약문이 반환값에 포함된다)을 테스트로 고정했다.

**교훈** — 검증기가 틀린 게 아니라 **측정이 틀렸다.** 실측을 신조로 삼는 프로젝트라도
"무엇을 재고 있는지"를 틀리면 없는 결함을 보고 있는 것을 만들어낸다. T-04와 짝이다 —
거기서는 통과하는 검증이 틀렸고, 여기서는 실패하는 검증이 틀렸다.

#### T-21 · 요약문으로 잰 "오탐 0" 이 실제 모델 문장을 덮지 못했다

**증상** — 근거 고정 검증기의 오탐률을 결정론적 요약문으로 재서 0%를 얻었다.
실제 모델(Gemini) 답변에 처음 돌리자 수치 4개가 잡혀 답변이 통째로 막혔다.

**확인** — 잡힌 값을 하나씩 대조했다. **셋 다 검증기의 오탐이었고 진짜 환각은 0건이었다.**

| 잡힌 값 | 모델이 쓴 자리 | 실제 |
|---|---|---|
| `0.014` | "스프레드가 0.014σ" | 도구는 `z: 0.014538`. 반올림(0.015)이 아니라 **버림** |
| `90` | "노이즈 수준(**p90**: 0.063)" | `noise_p90` 은 도구가 반환한 **키 이름** |
| `2` | "**2.** 연동 계열의 미동조" | 마크다운 **목록 번호** |

목록 번호가 특히 드러내는 게 있다. 같은 답변에서 **1과 3은 우연히 통과하고 2만
잡혔다** — 도구 반환값에 1.0과 3.000이 있었기 때문이다. 그 자체가 이 토큰들이
수치 주장이 아니라는 증거다.

**처리** — 셋 다 고쳤다. 버림을 마지막 자리 하나까지 인정하고, 도구 반환값의
**키 이름**에 든 숫자도 근거로 쓰고, 줄머리 목록 표식을 먼저 지운다.

**느슨해진 만큼 반대편을 다시 쟀다.** 처음엔 288건 중 6건이 통과해 97.9%가 나왔는데,
확인해 보니 그 6건은 전부 내가 손으로 고른 `0.019` 였고 도구가 실제로
`0.019862` 를 반환하고 있었다. **환각이 통과한 게 아니라 시험값이 실제 값과
겹친 것이다.** 무작위 204개 값으로 다시 재니 7,344건 **전부 차단**됐다.

**교훈** — T-20과 같은 자리에서 또 넘어졌다. 그때는 도구 반환 형태를 잘못 넘겼고,
이번엔 **문장 형태**를 잘못 잡았다. 결정론적 요약문에는 마크다운 목록도, 필드 이름
인용도, 버림 표기도 없다.

> **"측정했다"가 "옳게 측정했다"는 뜻이 아니다.** 실제 산출물에 돌려보기 전까지
> 내가 만든 표본이 무엇을 대표하는지 알 수 없다.

시험 데이터를 손으로 고른 것도 같은 문제였다. 실제 분포와 겹치는지 확인하지 않은
"조작값"은 조작값이 아니다.

#### T-22 · 답변 1건으로 잰 "오탐 0" 이 6건에서 네 종류를 더 냈다

**증상** — T-21 을 고친 뒤 실모델 답변 1건에서 오탐 0을 확인했다. 질문 유형을
바꿔 6건을 더 받자 **4건이 막혔다.**

**원인** — 네 종류였고 **전부 검증기의 오탐, 진짜 환각은 또 0건이었다.**

| 종류 | 모델이 쓴 것 | 무엇이 잡혔나 |
|---|---|---|
| 한국어 날짜 | `2026년 9월 5일` | 연·월은 우연히 통과하고 **일자만** |
| 식별자 | `c4e54b3d-550c-4a9b-…` | 조각 9개. 하이픈을 음수로 읽어 **`-550`** 까지 |
| ISO 시각 | `2026-09-08T00:55:13.508517+00:00` | 날짜만 떼고 남은 **`508517`** |
| 재포맷 시각 | `2026-09-08 00:55:13` | 도구 값과 형식이 달라 통째로 |

**식별자 건이 특히 고약했다.** 처음 쓴 테스트가 통과해 버렸는데, UUID 조각이
도구 반환값에도 조각으로 들어 있어 **각각 우연히 맞았기 때문**이다. 내가 바로
앞에서 비판한 그 현상을 테스트가 다시 저지르고 있었다. 조각이 맞는지가 아니라
**식별자 전체가 하나의 토큰으로 처리되는지**를 검사하도록 다시 썼다.

같은 이유로 원래 실행에서 그 답변이 통과했던 것도 우연이었다 — `exception_id`
가 프롬프트에 있어서 **자기 조각이 자기를 근거로 만들고 있었다.**

**처리** — 시각 → 식별자 → 날짜 → 숫자 순서로 통째로 먼저 걷어낸다. 재포맷한
시각은 숫자만 남긴 접두 비교로 맞춘다.

**재측정** — 답변 6건 검사 토큰 69개 **오탐 0**, 조작 주입 **1,266건 전부 차단**.

**교훈** — T-21 에서 "요약문으로 잰 0% 가 실제 문장을 못 덮었다"고 적고, 이번엔
**답변 1건으로 잰 0% 가 6건을 못 덮었다.**

> 표본이 덮는 형태만큼만 안다. "오탐 0" 은 **어떤 표본에서인지**와 함께 적어야
> 의미가 있다.

### 1.5 저장·런타임

#### T-11 · 두 번째 연결이 앞선 쓰기를 보지 못한다

**증상** — 파이프라인이 적재를 끝냈는데 조회 CLI에 데이터가 없었다.

**원인** — `Warehouse` 에 연결을 닫는 방법이 없었다. 같은 DuckDB 파일에 두 번째 연결을
열면 앞선 연결이 잡고 있어 쓰기가 보이지 않는다.

**처리** — `close()` 와 컨텍스트 매니저(`__enter__`/`__exit__`)를 추가했다.

#### T-12 · DuckDB가 없는 경로를 조용히 만든다

**증상** — 존재하지 않는 창고 경로를 줬는데 에러 없이 "근거 없음"이 기록됐다.

**원인** — DuckDB는 없는 파일을 새로 만든다. 빈 DB에서 근거를 조립하니 당연히 아무것도
없고, 그 결과가 **진짜 판정처럼** 원장에 남는다.

**처리** — 경로 존재를 먼저 확인하고, 없으면 열지 않고 "권고 없음"으로 남긴다.

**교훈** — **모으지 못한 것과 모아서 없는 것은 감사에서 전혀 다른 의미다.**
경로 오타 하나가 그 구분을 지웠다.

#### T-13 · `current_date` 가 타임존 의존성을 요구한다

**증상** — 신선도 뷰가 `TIMESTAMPTZ` 비교에서 pytz를 요구하며 실패했다.

**처리** — 뷰가 현재 시각을 스스로 정하지 않고 `as_of` 를 **명시적으로 받도록** 바꿨다.
`check_quality` 도 `as_of` 를 받으므로 기준이 한 곳으로 모인다.

**교훈** — 시간을 함수 안에서 읽으면 테스트가 어려워지고 기준이 흩어진다.

### 1.7 절차

#### T-18 · 근거를 확인하지 않은 승인이 원장에 남아 있었다

**증상** — 승인 보조 도구를 완성하고 **이 프로젝트 자신의 감사 로그**에 처음 돌렸더니,
이미 승인된 건이 `reject_likely` 로 나왔다.

**확인** — 권고가 맞았다.

| | 실제 |
|---|---|
| 2026-09-04 기준금리 | 3.000, 전일 대비 **+0.000** |
| 같은 날 콜금리 | +0.006 (평시 상위 10%인 0.063 미만) |
| 적재 이력 최대 변동폭 | 0.25 — **0.9는 존재한 적이 없다** |
| request_id | `req-demo` — 실제 수집이 아닌 데모 항목 |

**0.9 급변은 일어난 적이 없다.** 그런데 "금통위 인상 확인"이라는 그럴듯한 사유와 함께
통과해 있었다. (데모 과정에서 만든 것이지 운영 사고는 아니다.)

**교훈** — 기존 게이트는 이걸 잡을 수 없었다. **사유가 비어 있지 않고 승인자가 있으면
통과**이기 때문이다.

> **사유란은 사람이 무엇이든 쓸 수 있다.** 감사 로그는 그것을 그대로 보존한다.
> 잡으려면 승인 시점의 근거를 나중에 재구성할 수 있어야 한다.

**처리** — 이 승인은 이후 철회됐다(D-12). 감사 로그에는 세 줄이 남는다.

```
staged    pending   by=-       revoked_by=-
approved  approved  by=mason   revoked_by=-
revoked   revoked   by=mason   revoked_by=mason
```

원래 결정과 사유(`금통위 인상 확인`)는 **지우지 않았다.** 누가 무엇을 근거로
승인했었는지가 남아야 감사가 성립한다.

## 2. 엔지니어링 결정

각 항목은 **무엇을 포기했는지**까지 적는다. 대가 없는 결정은 결정이 아니다.

### D-01 · 오염 카탈로그를 게이트 구현 **전에** 고정한다

**상황** — 차단율을 측정해야 하는데, 게이트를 만든 뒤 오염을 고르면 결과가 자기충족적이 된다.

**결정** — 오염 9종을 설계 문서에 먼저 커밋(`88a07c9`, 10:48)하고 게이트를 그 뒤에
만들었다(10:55~11:54). **목표 차단율도 사전에 선언하지 않았다** — 정하면 그 숫자를
맞추도록 게이트를 조정하게 된다. 개발 중 발견한 2종은 **사후 추가로 구분 표기**했다.

**대가** — 카탈로그가 실제 위협을 다 담지 못했을 수 있다. 그래도 사후에 고르는 것보다 낫다.

**검증 가능성** — 커밋 타임스탬프 순서로 증명된다.

### D-02 · 근거 수집은 LLM이 아니라 결정론적 probe로 한다

**상황** — 승인 보조는 "에이전트가 근거를 모아 제안한다"는 구조다. 근거 요약을 LLM에
맡길 수도 있었다.

**결정** — probe 5종을 전부 SQL과 파일 대조로 구현했다. 각 probe는 판정과 **그 판정의
근거가 된 숫자**를 함께 반환한다.

**왜** — "콜금리가 동행했다"는 문장이 틀렸는데 그것을 근거로 승인이 이뤄지면, 나중에
추적해도 왜 통과했는지 알 수 없다. **감사가 필요한 시스템에서 근거는 재현 가능해야 한다.**

**대가** — 자연어 설명의 유연함을 잃는다. probe 를 늘리려면 코드를 짜야 한다.

**남는 여지** — LLM은 이 probe들을 **호출하는 쪽**에 있을 수 있다. 근거의 진위가 LLM에
의존하지 않는 것이 핵심이다.

### D-03 · 권고는 승인자가 신고하지 않고 시스템이 계산해 기록한다

**상황** — "사람이 에이전트와 다른 판단을 한 적이 있는가"를 감사하려면 승인 시점의 권고를
남겨야 한다. 승인자에게 `--saw-recommendation` 으로 적게 할 수도 있었다.

**결정** — `fingate-gate approve` 가 결정 시점에 리뷰어를 직접 돌려 권고를 계산해 기록한다.

**왜** — 자기 신고면 거수기 탐지가 무의미해진다. 거수기인 사람이 정직하게 신고할 이유가 없다.

**대가** — 게이트 CLI가 창고·원본 저장소 경로를 알아야 한다. 근거 수집이 실패해도
**승인 자체는 막지 않는다**(게이트를 여는 유일한 경로를 부수적 실패로 잠그면 안 된다).

**따라 나온 것** — `fingate-gate audit` 의 100% 일치는 좋은 신호가 아니다.
**거수기를 탐지할 수 없는 승인 절차는 승인 절차가 아니다.**

### D-04 · 리뷰어는 원장을 변경할 수 없다

**결정** — `fingate-review` 는 승인·반려를 실행하는 경로에 접근하지 않는다.
**코드 규약이 아니라 테스트로 강제한다** — `ledger.approve/reject/stage` 를 예외를
던지도록 바꿔 놓고도 리뷰가 정상 동작하는지 검사한다.

**왜** — 권고와 결정의 경계가 코드에서 흐려지면, 문서에 무엇을 적든 실제로는 자동 승인이 된다.

**대가** — 승인이 2단계가 된다(`review` → `approve`). 그게 요점이다.

### D-05 · 회계 항등식은 허용 오차 없이 정확 비교한다

**상황** — 자산 = 부채 + 자본. 반올림 오차를 감안해 상대오차 허용치를 둘 수도 있었다.

**측정** — 검사 가능한 50개 회사-분기 전부에서 **상대오차 0.000e+00**.

**결정** — 정확 비교.

**대가** — 반올림이 있는 다른 원천에서는 이 규칙을 재검토해야 한다. 문서에 명시했다.

**왜** — 허용 오차를 두면 그만큼의 실제 결함을 놓친다. 오차가 0인데 여유를 둘 이유가 없다.

### D-06 · 부호 규칙은 지표마다 다르게 적용한다

**상황** — "금액이 음수면 이상"은 단순하고 매력적인 규칙이다.

**측정** — 저량 지표(자산·부채·자본·이익잉여금·보험계약부채)는 음수 **0건**.
그러나 유량 지표는 음수가 **실제로 존재**한다 — net_income 1건, operating_income 2건,
interest_expense 4건. **적자 분기다.**

**결정** — 저량 지표에만 부호 규칙을 적용한다.

**대가** — 지표 목록을 유지해야 한다. 새 지표를 추가할 때 어느 쪽인지 정해야 한다.

**만약 일괄 적용했다면** — 정상적인 적자 분기 7건을 차단했을 것이다.

### D-07 · 재무제표 기준을 **선언**하고, 없으면 대체하지 않는다

**상황** — DART가 연결·별도를 함께 준다(T-04). 세 가지 선택지가 있었다.

| 안 | 내용 | 문제 |
|---|---|---|
| A | 둘 다 저장(PK에 `fs_div` 포함) | 서빙 뷰가 어느 쪽을 쓸지 여전히 정해야 함. 결정을 미룰 뿐 |
| B | 연결 우선, 없으면 별도로 대체 | 행마다 기준이 달라져 회사 간 비교가 깨짐 |
| **C** | **연결을 계약으로 선언, 없으면 차단** | 별도만 제출하는 대상은 다룰 수 없음 |

**결정** — C. 보험그룹 비교의 표준이 연결이고, 이 제품의 목적이 회사 간 비교다.

**대가** — 별도 기준 분석에는 계약 변경이 필요하다. 두 기준을 동시에 서빙하지 않는다.

**왜 B가 아닌가** — 조용한 대체는 정확히 T-04를 다시 만드는 길이다. 행마다 기준이
다른데 아무도 모르는 상태가 된다.

**보완** — 채택하지 않은 기준의 행은 버리지 않고 `OTHER_BASIS` 로 기록한다(869건).
조용히 버리면 나중에 왜 그 값인지 추적할 수 없다.

### D-08 · 승인은 만료되고, 승인된 값은 기준선으로 승격된다

**결정** — 승인에 TTL을 둔다. 승인된 데이터는 last-known-good 스냅샷으로 승격한다.

**결과로 따라오는 것** — 나중에 승인이 만료되고 새 위반이 생기면, degraded로 내보내는
last-known-good 안에 **그때 승인했던 값**이 들어 있다.

**의도된 동작이다.** 승인은 "이 값은 정당하다"는 사람의 판단이고, 만료는 "새로운 위반까지
자동으로 통과시키지는 않는다"는 뜻이지 과거 판단을 소급 무효화한다는 뜻이 아니다.

**대가** — **잘못된 승인은 기준선에 남는다.** 되돌리려면 사람이 개입해야 한다.
이것이 승인 주체와 사유를 감사 로그에 반드시 남기는 이유다.

### D-11 · 관계의 종류를 둘로 나눈다 — 동행과 앵커

**상황** — `call_rate_daily` 에 자격 peer 가 하나도 없었다. 동행률은 **앵커가 움직인 날**을
조건으로 계산하는데, 기준금리는 899일 중 892일 평평하다. 그 계열이 차단되면 리뷰어가
영원히 `INSUFFICIENT` 만 냈다.

**관찰** — 그런데 콜금리와 기준금리의 관계는 애초에 "함께 변한다"가 아니다. 콜금리는
정책금리 **수준을 따라가는** 전달 금리다.

**측정** — 스프레드(대상 − 앵커) 안정성을 전 쌍에서 쟀다.

| 쌍 | 표준편차 | 겹침 |
|---|---|---|
| **콜금리 − 기준금리** | **0.0593** | 900 |
| 국고채 10y − 3y | 0.1553 | 901 |
| 대출평균 − 기준금리 | 0.2314 | 43 |
| 기준금리 − 국고채 3y | 0.5041 | 900 (너무 헐거움) |

**결정** — 동행(`peer_corroboration`)과 앵커(`anchor_spread`)를 **별도 근거로** 둔다.

**왜 하나로 합치지 않는가** — 다른 질문에 답한다. 동행은 "앵커가 함께 움직였나",
앵커는 "수준 관계가 유지됐나"다. 앵커가 거의 안 움직이는 계열에서는 전자가 성립하지
않는다. **합치면 그 사각지대가 그대로 남는다.**

**자격 조건에 검출 가능성을 넣었다** — 스프레드가 흔들리는 만큼 급변이 묻힌다.
계약 위반 크기의 변동이 경보를 넘기지 못하는 앵커는 제외한다. 기준금리×국고채가
그 경우다(급변 0.75가 표준편차 0.5041 안에 묻힌다).

**충돌하면 한쪽을 고르지 않는다** — 두 근거가 갈리면 `INSUFFICIENT_EVIDENCE` 로
그 사실을 알린다. 갈린다는 것 자체가 승인자에게 필요한 정보다.

**대가** — probe 가 하나 늘어 화면이 길어진다. 계열마다 어떤 근거가 적용 가능한지
달라진다.

**결과** — 모든 계열이 최소 한 종류의 근거를 갖게 됐다.

| 계열 | 동행 peer | 앵커 |
|---|---|---|
| call_rate_daily | 없음 | **base_rate** ← 메워짐 |
| bank_loan_household | avg | 없음 |
| 나머지 4개 | 있음 | 있음 |

### D-12 · 철회는 기록을 지우지도, 스냅샷을 되돌리지도 않는다

**상황** — D-08은 "잘못된 승인은 기준선에 남는다. 되돌리려면 사람이 개입해야 한다"고
규정했다. 그런데 **개입할 경로가 코드에 없었다.** 원장은 append-only 인데 철회 연산이
없었고, T-18의 근거 없는 승인을 발견하고도 정정할 방법이 없었다.

**결정** — `revoke` 를 추가하되 두 가지를 하지 않는다.

| 하지 않는 것 | 왜 |
|---|---|
| 원래 결정을 지우지 않는다 | 누가 무슨 사유로 승인했었는지가 남아야 감사가 성립한다 |
| 승격된 스냅샷을 되돌리지 않는다 | 자동으로 하면 "승인은 사람의 판단"이라는 전제가 깨진다 |

**하는 것은 하나다** — 이 예외가 더 이상 시계열을 통과시키지 못하게 한다.
철회해도 계속 통과하면 아무 의미가 없다.

**대칭성** — 반려도 철회할 수 있다. 되돌릴 경로가 승인에만 있으면 비대칭이고,
반려도 틀릴 수 있다.

**대기 중인 건은 철회 대상이 아니다** — 그건 반려하는 것이다.

**철회된 결정은 일치도 표본에서 빠진다** — 철회된 결정을 승인자의 판단력에 대한
근거로 쓰지 않는다. 대신 `fingate-gate audit` 이 철회 건수를 따로 보여준다.

### D-13 · LLM은 도구를 호출하는 쪽에 두고, 답변에도 게이트를 건다

**상황** — D-02에서 근거 수집을 결정론적 probe 로 구현하기로 하면서 이렇게 적었다.

> LLM은 이 probe들을 **호출하는 쪽**에 있을 수 있다. 근거의 진위가 LLM에
> 의존하지 않는 것이 핵심이다.

그 자리를 실제로 채웠다.

**결정 1 — 도구 이름은 `read_evidence` 다.** probe 6종은 어차피 함께 계산된다.
에이전트는 계산을 고르는 것이 아니라 **읽을 것을 고른다.** `run_probe` 라고 부르면
전사에 "에이전트가 anchor_spread 를 실행했다"고 남는데 사실이 아니다.

**결정 2 — 답변에도 fail-closed 를 적용한다.** 답변의 모든 수치가 도구 반환값
또는 질문에서 왔는지 확인하고, 하나라도 근거가 없으면 **본문을 출력하지 않는다.**

금융에서 LLM 실패는 없는 수치를 그럴듯하게 말하는 형태로 온다. 승인자가 그것을
근거로 게이트를 열면 T-18이 반복되는데, 이번에는 사유가 **모델이 지어낸 수치**다.

| 반올림 처리 | 도구가 15.083 → 모델이 "15.1σ" 는 인정. "15.9σ" 는 잡는다 |
|---|---|
| 백분율 | 0.922 → "92.2%" 만 인정. `%` 없이 "92.2" 는 인정하지 않는다 |
| 날짜 | 통째로 대조한다. 숫자 셋으로 쪼개면 정상 답변이 환각으로 몰린다 |
| 질문에서 온 값 | 인정하되 **출처를 `prompt` 로 표시**한다. 지어낸 것은 아니지만 검증된 것도 아니다 |

**결정 3 — 수동 루프.** SDK 의 tool runner 를 쓰면 루프를 안 짜도 되지만,
(a) 모든 도구 반환값을 모아야 검증할 수 있고 (b) 자격 증명 없이 테스트해야 한다.
수집기가 전송 계층을 주입받는 것과 같은 규율이다. **CI 는 API 키 없이 돈다.**

**결정 4 — 거절을 다른 모델로 우회시키지 않는다.** SDK 는 `stop_reason: "refusal"`
일 때 서버측 fallback 으로 자동 우회시킬 수 있다. 켜지 않았다. 근거를 조립하는
도중에 모델이 조용히 바뀌면 **그 답변이 어느 모델에서 나왔는지 감사할 수 없다.**
이 프로젝트가 T-04에서 반대한 바로 그 형태의 조용한 대체다.

**대가** — 거절이 나면 답이 없다. 승인자는 `fingate-review` 로 근거를 직접 봐야 한다.
그게 맞다. 자동 우회는 편의를 주고 추적 가능성을 가져간다.

**측정** — 양쪽 다 쟀다. 근거 있는 문장의 수치 39개에서 **오탐 0**, 없는 수치
주입 180건 **전부 차단**. 다만 모든 문장 형태를 덮지는 않는다.

### D-09 · 조인 축을 연도에서 분기로

**상황** — IFRS17 단절로 보험사 재무가 2023년부터만 존재한다(T-05).

**결정** — 연도 조인을 버리고 분기 축으로. 금리는 분기 평균으로 집계해 붙인다.

**대가** — 비교 가능한 시점이 10개뿐이다. 그래서 상관 분석이 잡음이 된다(T-10).
**이 한계를 감추지 않고 CLI가 출력한다.**

### D-10 · 배포 스테이지를 만들지 않는다

**상황** — 포트폴리오 저장소에 CI/CD가 있으면 보기 좋다.

**결정** — `dev`(통합) → `main`(릴리스) 브랜치 모델과 버전 태그만 둔다.
**README에 "배포 스테이지는 없다"고 명시한다.**

**왜** — FinGate는 상시 구동 서버가 없는 로컬 파이프라인이다. 없는 배포 단계를 흉내 내면
"어디에 배포되나요" 한 마디에 무너진다. 검증되는 범위는 **"main에 있는 것은 CI를 통과한
상태"**까지다.

**부수 결정** — 브랜치 보호에 `enforce_admins` 를 켰다. 끄면 소유자는 그냥 통과한다.
**우회 가능한 게이트는 게이트가 아니라는 것이 이 프로젝트의 논지인데, 저장소 규칙만
우회 가능하게 두면 앞뒤가 맞지 않는다.**

검증: main에 직접 push를 시도했고 거부됐다.

```
remote: error: GH006: Protected branch update failed for refs/heads/main.
remote: - Required status check "test" is expected.
```

## 3. 반복해서 나타난 원칙

### 3.1 설계 전에 측정한다

**측정하지 않았으면 틀렸을 것들** — 전부 실제로 겪었다.

| 만약 추측했다면 | 실측 |
|---|---|
| HTTP 상태로 성공 판정 | 두 API 모두 오류를 200으로 반환 |
| 응답이 빠르니 여유 있다 | 0.12초 응답 → 초당 8건 → **실제로 차단당함** |
| 단위 라벨은 일관될 것 | `연%` / `연리%` 혼재 |
| 금리는 다 같이 움직인다 | 국고채 동행률 0.429 (동전 던지기 이하) |
| 월별 60일이면 충분 | 68일이 정상 → 정상 데이터 차단 |
| 금액 음수면 이상 | 적자 분기 7건이 정상 |
| 항등식이 맞으니 데이터가 맞다 | 두 기준이 각자 균형 → **아무것도 검증 못 하고 있었음** |

### 3.2 양쪽을 다 잰다

거짓 양성만 재면 아무것도 안 막는 게이트가 만점을 받는다. 거짓 음성만 재면 다 막는
게이트가 만점을 받는다.

| | 거짓 양성 | 거짓 음성 |
|---|---|---|
| 금리 계약 | 정상 데이터 서빙 유지 | 오염 11종 서빙 도달 90.9% → **0%** |
| 재무 계약 | 실데이터 50개 회사-분기 차단 **0건** | 오염 6종 **전부 차단**, +8% 정상 변동은 통과 |
| peer 자격 | 실측 자격 3쌍만 통과 | 무관한 쌍·추세 착시 전부 탈락 |

### 3.3 없는 것과 아닌 것을 구분한다

이 구분이 무너진 사례가 셋이나 나왔다.

| 상황 | 잘못 읽으면 | 실제 |
|---|---|---|
| `corr()` = `nan` | 완벽한 불일치 = 결함 | 판단할 근거 없음 |
| 빈 창고에서 나온 "근거 없음" | 진짜 판정 | 모으지 못한 것 |
| 금리 테이블에서 조회한 재무 전례 | 전례 없음 | 잘못된 곳을 보고 있음 |

**처리는 매번 같았다**: `INSUFFICIENT` 를 독립된 결과로 두고, 절대 방향을 가진 판정으로
접지 않는다. 화면에서는 똑같아 보이지만 의미가 정반대다.

### 3.4 약한 결과를 약하다고 표시한다

- 상관계수를 내되 **표본 수를 함께** 내고 경고를 출력한다(T-10)
- peer 판정에 상관·동행률·`lift`·표본 수를 **전부 노출**해 승인자가 스스로 가중치를 정한다
- `INSUFFICIENT_EVIDENCE` 를 부끄러워하지 않는다 —
  **근거가 없을 때 권고를 지어내는 것이 근거 없이 결정하는 것보다 나쁘다**
- README에 정직성 경계 표를 두고 실측/실험/설계 판단을 구분한다

### 3.5 결함은 대부분 실행이 찾았다

| 찾은 방법 | 발견 |
|---|---|
| **오염 주입** | T-04 연결·별도 혼입 (가장 큰 결함) |
| **실패한 테스트** | T-09 추세 착시, T-19 기준선 오염 |
| **실제 도구 실행** | T-18 근거 없는 승인 |
| **API 실호출** | T-01 HTTP 200, T-02 차단당함 |
| 코드 읽기 | 게이트가 ECOS 루프에만 있다는 사실 |

읽어서 찾은 것은 하나뿐이다. **나머지는 전부 돌려 봐야 나왔다.**

T-09와 T-19는 둘 다 **실패한 테스트**가 찾았다는 점에서 같다. 코드는 그럴듯했고
리뷰로는 넘어갔을 것이다. "이 입력에서 이 결과가 나와야 한다"를 먼저 적어 두지
않았다면 둘 다 그대로 남았다.
