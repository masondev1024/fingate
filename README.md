# FinGate

**잘못된 금융 수치가 사용자에게 닿기 전에 걸러낸다.**

한국은행에서 기준금리·국고채·대출금리를, 금융감독원에서 보험 5사 재무를 받아 하나의
표로 합쳐 내보낸다(이하 **서빙**). 받은 값이 **쓸 수 있는 값인지** 단계마다 확인하고, 확인을 통과하지
못한 값은 내보내지 않는다. 통과시키려면 사람이 근거를 보고 사유를 남겨 승인해야 한다.

## 왜 필요한가 — 금융에서 틀린 숫자의 값

금리 하나가 잘못 들어가면 그것으로 계산한 지표가 틀리고, 그 지표로 만든 리포트가 틀리고,
그 리포트로 내린 판단이 틀린다. 되돌리려면 어디서부터 틀렸는지 찾아 전부 다시 계산해야
한다. **틀린 값을 넣는 비용보다 찾아내는 비용이 훨씬 크다.**

그런데 데이터 파이프라인 대부분은 "받아서 넣었다"로 끝난다. 받은 것이 정말 쓸 수 있는
값인지 확인하는 단계 자체가 없다.

이 위험은 추상적이지 않다. 2026-09-07에 두 API를 직접 호출해 확인했다.

| 요청 | HTTP | 실제 본문 |
|---|---|---|
| ECOS, 잘못된 인증키 | **200** | `{"RESULT":{"CODE":"INFO-100", ...}}` |
| ECOS, 없는 통계표 코드 | **200** | `INFO-200` 오류 페이로드 |
| DART, 잘못된 인증키 | **200** | `{"status":"010", ...}` |
| DART, 요청 과다 | **200** | `{"status":"101", ...}` |
| DART `corpCode.xml` | **200** | **150 bytes** XML 오류 (정상은 3,601,634 bytes zip) |

**두 API 모두 모든 오류에 HTTP 200을 반환한다.** 즉 "요청이 성공했다"는 신호와 함께
오류 메시지를 보낸다. 상태 코드만 확인하는 흔한 방식으로는 그 오류 메시지가 그대로
금리 값 자리에 들어간다. 아무도 실패했다는 사실을 모른 채로.

## 결과

사전 등록한 오염 11종으로 게이트 유무를 비교했다.

| 지표 | 값 |
|---|---|
| 잘못된 데이터가 사용자에게 도달한 비율 | **90.9% → 0.0%** |
| 사전 등록 9종만 | 88.9% → 0.0% |
| 차단 계층 분포 | response 4, schema 4, quality 3 |
| 정상 데이터 13,173관측 | **하나도 막지 않음** (거짓 양성 0) |

오염 카탈로그는 게이트 구현 **전에** 설계 문서에 고정했다(커밋 `88a07c9`). 목표 차단율은
선언하지 않았다. 목표를 정하면 그 숫자를 맞추도록 게이트를 조정하게 된다.

상세: [`reports/fault-injection.md`](reports/fault-injection.md)

## 산출물

금리 환경과 보험 5사 재무를 분기 축으로 조인한 서빙 테이블 (2023 Q3 ~ 2025 Q4, 50행).

| 회사 | 연도 | 분기 | 자산총계(조) | 분기순이익(억) | 유도 | 기준금리 |
|---|---|---|---|---|---|---|
| 한화생명 | 2024 | 3 | 118.8 | 2,368 | | 3.50 |
| 한화생명 | 2024 | 4 | 122.1 | 1,360 | 예 | 3.18 |
| 한화생명 | 2025 | 1 | 125.8 | 1,220 | | 2.90 |
| 한화생명 | 2025 | 4 | 125.8 | −25 | 예 | 2.50 |

**4분기 손익은 DART가 직접 주지 않는다.** 사업보고서의 손익은 연간 전체이므로
`연간 − 3분기 누적`으로 유도하고, 유도값임을 플래그로 표시한다.

## 구조

```
수집 → [응답 계약] → 원본 보존(계보) → [스키마 계약] → [품질 계약] ─┬─ 통과 → 서빙
                                                                │
                                                    위반 → StagedException
                                                                │
                                                    담당자 승인/반려 → 감사 로그
```

### 세 번 확인한다 — "계약"이란 무엇인가

여기서 **계약(contract)** 은 법적 계약이 아니라 **데이터가 지켜야 할 약속**이다.
"이 값은 이런 형태로, 이런 범위 안에서 올 것이다"를 코드에 미리 적어 두고, 실제로
들어온 값이 그 약속을 지켰는지 확인한다. 지키지 못하면 통과시키지 않는다.

약속을 세 단계로 나눈다. 앞 단계를 통과해도 뒤 단계에서 걸릴 수 있다.

| 계층 | 확인하는 것 | 잡는 실패의 예 |
|---|---|---|
| **응답** | 이 응답이 정말 성공인가 | HTTP 200으로 온 오류 메시지, zip 자리에 온 150바이트, 호출 차단 |
| **스키마** | 형태와 의미가 맞는가 | 다른 시계열이 왔는데 값은 정상으로 보임, 단위 표기 변경, 빠진 항목 |
| **품질** | 이 값이 있을 수 있는 값인가 | 범위 밖 값, 하루에 있을 수 없는 급변, 중복, 너무 오래된 값, 빈 결과 |

**세 번째가 가장 어렵다.** 형식이 완벽한데 값이 틀린 경우가 실제로 위험하기 때문이다.
그래서 "있을 수 있는 값"의 범위를 추측하지 않고 11년치 실측 분포에서 유도했다.

### 막았을 때 무엇을 내보내는가

확인을 통과하지 못했다고 아무것도 안 내보내면 소비자 쪽이 멈춘다. 그렇다고 낡은 값을
최신인 척 내보내면 그게 더 위험하다. **직전에 정상이었던 값을 내보내되, 그것이 최신이
아니라는 사실과 마지막으로 정상이었던 시각을 함께 알린다.**

| 상태 | 의미 |
|---|---|
| `fresh` | 계약 통과, 최신 서빙 |
| `approved_override` | 위반이 있으나 유효한 사람 승인 존재 |
| `degraded` | 위반, 승인 없음 → 직전 정상 스냅샷 + 상태 명시 |
| `blocked` | 위반, 승인도 직전 스냅샷도 없음 |

## 설계에서 실측이 바꾼 것

추측으로 정했으면 틀렸을 것들이다.

- **단위 라벨이 일관되지 않는다.** 같은 연이율인데 대부분 `연%`, 가계대출금리만 `연리%`.
  원본 라벨과 정규화된 의미를 분리했다.
- **월별 신선도 SLA 60일이 정상 데이터를 막았다.** 예금은행 가중평균금리는 익월 말경
  공표되므로 기간 시작일 기준 68일이 정상이다. 95일로 조정했다.
- **급변 임계 0.5%p는 너무 빡빡했다.** 기준금리 빅스텝 0.50%p는 실제로 있었던 정상 변동이다.
  11년치를 재고 그 위인 0.75로 뒀다.
- **보험사 재무는 2023년부터만 존재한다.** 삼성전자는 2019~2022가 다 있으므로 API 제약이
  아니라 IFRS17 시행에 따른 단절이다. 조인 축을 연도에서 분기로 바꿨다.
- **응답이 빠를수록 위험하다.** DART가 0.12초에 응답하므로 페이싱 없이 호출하면 초당 8건이
  나간다. 실제로 25건 연속 호출에서 차단당했다.
- **사업보고서의 손익은 연간치다.** 분기로 오인하면 규모가 크게 부풀려진다. 3분기보고서는
  기간을 `2024.01.01~09.30`으로 표기하면서 금액은 3개월치를 준다. 날짜 범위를 믿으면 틀린다.
- **응답 순서가 데이터의 의미를 정하고 있었다.** DART는 같은 계정을 연결재무제표와
  별도재무제표 두 벌로 보낸다(실측 56/56 보고서). 중복을 접는 코드와 `ON CONFLICT DO UPDATE`가
  마지막 행을 채택해, 창고 전체가 **별도재무제표**가 되어 있었다(238/238). 아무도 그렇게
  정하지 않았다. 한화생명 2024 기준 연결 160.1조 vs 별도 122.1조로 **38조 차이**다.
  연결을 계약 기준으로 선언하고 `fs_div`를 행에 기록했다.

```bash

```

실행하면 금리 4,132행과 보험 5사 재무 900행이 적재되고 서빙 테이블 50행이 만들어진다.
실측 소요 1분 41초.

### 차단된 건을 승인하기

품질 계약 위반은 자동으로 서빙을 막는다. 정당한 급변(정책금리 인상, 회계기준 변경)은
담당자가 근거를 보고 통과시킨다.

```bash
uv run fingate-gate list                    # 승인 대기 목록
uv run fingate-gate show <id>               # 위반 근거와 계보
uv run fingate-gate approve <id> --by 이름 --note "금통위 인상 확인"
uv run fingate-gate reject  <id> --by 이름 --note "수집 오류로 판단"
uv run fingate-gate revoke  <id> --by 이름 --note "재검토 결과 근거 없음"
```

`revoke` 는 이미 내린 결정을 되돌린다. **원래 결정과 사유는 지우지 않는다** — 누가
무엇을 근거로 승인했었는지가 남아야 감사가 성립한다. 이미 승격된 last-known-good
스냅샷도 되돌리지 않는다. 하는 일은 하나다: 이 예외가 더 이상 시계열을 통과시키지
못하게 한다.

사유 없는 결정은 거부된다. 모든 결정은 감사 로그에 남고, 대장 상태는 그 로그에서
복원되므로 파이프라인과 별도 프로세스에서 승인해도 반영된다.

### 승인 보조 — 근거를 조립해 제시하되 승인하지 않는다

`show` 가 주는 것은 `0.9 exceeds 0.75` 뿐이다. 이걸로는 결정할 수 없다. 승인자가 실제로
답해야 하는 질문은 **"진짜 시장 움직임인가, 우리 데이터가 망가진 것인가"**이고, 두 경우의
정답은 정반대다.

```bash
uv run fingate-review <id>          # 근거 5종 + 권고
uv run fingate-review <id> --json   # 기계 판독용
```

probe 다섯 개는 전부 SQL과 파일 대조로 구현된 **결정론적** 도구다. 근거 수집이 환각하면
감사 로그가 오염되고 왜 통과시켰는지 추적할 수 없게 된다.

| probe | 답하는 질문 |
|---|---|
| `peer_corroboration` | 연동된 다른 금리도 같은 날 같은 방향으로 움직였나 |
| `anchor_spread` | 앵커와의 **수준 관계**가 유지됐나 (앵커가 움직이지 않아도 성립) |
| `raw_provenance` | 이 값이 보존된 원본 응답에 실제로 있나 |
| `historical_precedent` | 같은 임계를 넘은 전례가 있나 |
| `blast_radius` | 반려하면 서빙 몇 행이 degraded가 되나 |
| `prior_decisions` | 같은 계열·규칙을 과거에 어떻게 결정했나 |

**연동 계열은 믿음이 아니라 측정으로 정한다.** 전체 쌍을 재보니 자격을 갖춘 쌍은 셋뿐이었다.
국고채 3y↔10y(동행률 0.922), 기준금리→콜금리(1.000, 변동 7회), 대출평균↔가계대출(0.763).
기준금리↔국고채는 0.429로 동전 던지기보다 나빴다 — 국고채가 정책 결정을 선반영하기 때문이다.

동행과 앵커는 **다른 질문에 답한다.** 동행률은 앵커가 움직인 날을 조건으로 하므로,
기준금리처럼 899일 중 892일 평평한 계열에는 성립하지 않는다. 실제로 `call_rate_daily`
에는 자격 peer 가 하나도 없었다. 그런데 콜금리−기준금리 **스프레드는 표준편차 0.0593**
으로 데이터에서 가장 단단한 관계다. 관계의 종류가 달랐던 것이다.

두 근거가 갈리면 한쪽을 임의로 채택하지 않고 갈린다는 사실을 알린다.

`fingate-review` 는 원장을 변경할 수 없다. 테스트로 강제한다.

### 승인이 형식으로 굳는지 감시하기

```bash
uv run fingate-gate audit
```

승인 시점에 **시스템이 직접 계산한** 권고를 원장에 함께 남기고, 사람의 결정과 얼마나
일치했는지 센다. 승인자에게 물어 적게 하면 자기 신고가 되어 의미가 없다.

100% 일치는 좋은 신호가 아니다. 근거를 보지 않고 권고를 그대로 누르고 있다는 뜻일 수 있다.
**거수기를 탐지할 수 없는 승인 절차는 승인 절차가 아니다.**

이 도구를 만들고 프로젝트 자신의 감사 로그에 처음 돌렸더니, 이미 승인되어 있던 건이
`reject_likely` 로 나왔다. 확인해 보니 문제의 0.9 급변은 **일어난 적이 없었고**(당일
기준금리는 3.000, 전일 대비 +0.000) 원본 응답도 없었다. 그런데 "금통위 인상 확인"이라는
사유와 함께 통과해 있었다. 사유란은 사람이 무엇이든 쓸 수 있다.

### 조회

```bash
uv run fingate-query serving                 # 금리 x 재무 서빙 테이블
uv run fingate-query change --corp 한화생명    # 분기 대비 변화 (윈도우 함수)
uv run fingate-query sensitivity             # 금리 민감도
uv run fingate-query freshness               # 시계열 신선도
```

`sensitivity` 는 상관계수와 함께 **비교에 쓴 분기 수**를 낸다. IFRS17 시행(2023)으로
보험사 재무가 2023년부터만 존재해 시점이 10개뿐이므로, 현재 상관계수는 신호가 아니라
잡음이다. CLI가 그 경고를 함께 출력한다.

### 재무 데이터도 같은 규율을 받는다

초기 구현에서 품질 계약과 승인 게이트는 **금리에만** 걸려 있었다. 보험사 재무는 응답
계약만 통과하고 곧바로 적재됐다. 그런데 서빙 테이블 50행 전부를 구동하는 것이 재무이고
금리는 `LEFT JOIN`으로 붙는 맥락이다. 게이트가 걸린 쪽이 덜 중요한 절반이었다.

재무 품질 규칙도 전부 실측에서 유도했다.

| 규칙 | 실측 근거 |
|---|---|
| 대차 불일치 | 자산 = 부채 + 자본이 50/50에서 상대오차 **0.000e+00** |
| 저량 지표 음수 | 자산·부채·자본·잉여금·보험계약부채 음수 **0건** |
| 필수 지표 결측 | 5사 × 10분기 총자산·자본·손익 **10/10 존재** |
| 총자산 급변 | 분기 변동 **−2.88% ~ +8.73%**, p95 6.14% → 임계 25% |

손익과 이자비용은 **음수가 정상**이다(적자 분기가 실제로 있다). 일괄 "음수 금지"는
정상 데이터를 막는다.

양쪽 다 쟀다. 실데이터 재실행에서 재무 품질 차단 **0건**(거짓 양성 없음), 실제 보존된
DART 원본에 오염을 주입해 6종 전부 차단(거짓 음성 없음). 실측 최대와 같은 +8% 변동은
통과한다.

## 브랜치와 릴리스

| 브랜치 | 역할 |
|---|---|
| `main` | 릴리스. 태그가 붙는 지점. 직접 push 불가, `dev` 에서 PR로만 들어온다 |
| `dev` | 통합. 기능 브랜치가 여기로 모인다 |
| `feat/*`, `fix/*`, `chore/*` | 작업 단위. `dev` 에서 분기해 `dev` 로 PR |

CI는 `main`·`dev` push와 두 브랜치를 대상으로 하는 PR에서 실행된다. lint, 포맷 검사,
전체 테스트가 통과해야 병합할 수 있다. 테스트는 외부 API 자격 증명 없이 돌아간다 —
수집기 테스트가 전송 계층을 주입해 네트워크를 타지 않기 때문이다.

**이 저장소에 배포 스테이지는 없다.** FinGate는 로컬에서 실행하는 파이프라인이고
상시 구동되는 서버가 없다. 없는 배포 단계를 흉내 내는 대신 릴리스 경계만 둔다.
실제로 검증되는 것은 "main에 있는 것은 CI를 통과한 상태"까지다.

## 정직성 경계

| 항목 | 성격 |
|---|---|
| 두 API의 HTTP 200 오류 반환 | **실측** |
| 수집한 금리·재무 수치 | **실데이터** |
| 주입한 오염 7종 | **합성** — 실제 사고 사례가 아님 |
| 차단율 90.9% → 0% | **실험 결과** — 운영 실적이 아님 |
| 신선도 SLA 임계값 | **설계 판단** — 업계 표준이 아님 |
| 재무 계약 기준 = 연결(CFS) | **설계 선언** — 별도 기준 분석에는 계약 변경 필요 |
| 총자산 급변 임계 25% | **실측 유도** — 10분기 관측 기반, 표본이 늘면 재측정 필요 |
| 연동 계열 자격 임계 | **실측 유도** — 2023–2026 적재분 기준, 다른 데이터에선 재측정 필요 |
| 기준금리→콜금리 동행률 1.000 | **실측이지만 변동 7회 표본** — 일반 법칙이 아님 |
